01

왜 만들었나

금융권이 생성형 AI 도입에서 가장 먼저 막히는 지점은 성능이나 정확도가 아니라 통제입니다. 개인신용정보가 외부로 나가는 것을 막을 수 있는가, 누가 무엇을 보냈는지 사후에 재구성할 수 있는가, 그리고 그 통제가 망분리 규제 안에서 성립하는가입니다.

전자금융감독규정은 금융회사의 내부 업무망을 외부 통신망과 분리하도록 요구합니다. 최근 금융당국은 생성형 AI 활용을 위해 이 규제를 단계적으로 완화하는 방향을 제시했고, 완화의 조건은 대체로 접근 통제 · 전송 데이터 통제 · 로깅으로 모입니다.

KAIROS는 이 세 조건을 하나의 계층에서 만족시키는 것을 목표로 합니다. 업무망은 인터넷에 나갈 수 없고, 통제된 단일 출구 하나만 허용된다. 그 출구가 KAIROS입니다.

02

망분리 — 이 프로젝트의 중심

가장 중요한 설계 판단은 보안 그룹이 아니라 라우팅 테이블로 막았다는 것입니다.

보안 그룹은 규칙을 잘못 고치면 뚫립니다. 설정으로 막았다는 상태입니다. 경로가 없는 서브넷은 나갈 방법 자체가 없습니다. 구조적으로 못 나간다는 상태입니다. 이 차이가 감사에서 설명해야 하는 지점이고, KAIROS가 전체에 걸쳐 지킨 기준이기도 합니다.

VPC 10.0.0.0/16 · ap-northeast-2
Public 10.0.1.0/24 0.0.0.0/0 → IGW
NAT + Squid t4g.micro
App 10.0.11.0/24 0.0.0.0/0 → NAT
KAIROS PostgreSQL t4g.small
Workload · 업무망 10.0.12.0/24 기본 경로 없음
내부 클라이언트 t4g.micro

업무망 라우팅 테이블에는 0.0.0.0/0 경로가 없습니다. Terraform 코드에서 확인해야 할 것은 무엇이 있는가가 아니라 무엇이 없는가입니다.

프록시를 KAIROS와 같은 호스트에 두지 않은 이유

프록시가 애플리케이션과 같은 호스트에 있으면, 프록시 설정을 지우는 것만으로 우회됩니다. 그러면 프록시는 통제가 아니라 권고사항입니다.

별도 인스턴스에 두고 전달 트래픽의 443을 끊으면 프록시를 거치지 않고는 나갈 수 없습니다. Squid는 그 인스턴스에서 자기 이름으로 나가므로 OUTPUT 체인을 타고 이 규칙에 걸리지 않습니다.

업무망→ KAIROS→ Squid→ NAT→ api.openai.com ALLOW
업무망╳인터넷 라우팅 없음
KAIROS╳443 직결 FORWARD REJECT
KAIROS→Squid╳허용 목록 밖 403

Squid는 HTTPS를 복호화하지 않습니다. CONNECT의 목적지 도메인만 보고 판정합니다. 실무에서 AWS Network Firewall이나 보안 웹 게이트웨이가 맡는 역할을 비용 제약 때문에 대체한 것이며, 판정 방식은 동일합니다. 한계를 알고 대체했다는 점을 문서에 명시했습니다.

Terraform — 확인해야 할 것은 "무엇이 없는가"

resource "aws_route_table" "workload" {
  vpc_id = aws_vpc.main.id
  # 0.0.0.0/0 경로가 없다. 이 파일에서 가장 중요한 것은 없는 쪽이다.
  tags = { Note = "no default route on purpose" }
}

NAT — 프록시를 우회한 직결을 끊는다

# app 구간을 외부로 내보내되
iptables -t nat -A POSTROUTING -s 10.0.11.0/24 -o "$PRIMARY_IF" -j MASQUERADE

# 전달되는 443/80은 끊는다. 프록시를 거치지 않으면 나갈 수 없다.
iptables -A FORWARD -s 10.0.11.0/24 -p tcp --dport 443 -j REJECT
iptables -A FORWARD -s 10.0.11.0/24 -p tcp --dport 80  -j REJECT

# Squid는 이 호스트에서 자기 이름으로 나가므로 OUTPUT 체인을 타고 위 규칙에 걸리지 않는다.

Squid — 거부가 허용보다 먼저

acl allowed_domains dstdomain "/etc/squid/allowed_domains.txt"
acl app_subnet      src 10.0.11.0/24

# 규칙은 위에서부터 평가된다. 허용을 먼저 두면
# 허용 도메인으로 가는 443 이외의 포트까지 함께 열린다.
http_access deny  CONNECT !SSL_ports
http_access deny  !app_subnet
http_access allow app_subnet allowed_domains
http_access deny  all

접속은 SSH가 아니라 SSM으로

22번 포트를 아예 열지 않았습니다. bastion도 키 파일도 없습니다. 무엇보다 누가 언제 어느 인스턴스에 붙었는지가 CloudTrail에 남습니다. 감사 관점에서 SSH 대비 가장 큰 차이입니다.

업무망은 인터넷이 없으므로 SSM에 닿으려면 VPC 엔드포인트가 필요합니다. 인터넷 없는 구간에서 AWS 서비스를 쓰려면 엔드포인트가 유일한 길이라는 제약이 이 구성에서 드러납니다.

03

아키텍처와 요청 흐름

모듈은 기술 계층이 아니라 책임으로 나눴습니다. controller / service / repository로 먼저 자르면 기능이 커질수록 한 패키지 안에 관계없는 것들이 쌓입니다.

auth JWT 발급·검증, refresh 세션 user 계정, 전역 역할(USER/ADMIN) tenant 조직 경계, tenant 내 역할(OWNER/ADMIN/MEMBER) project 기능 단위, 허용 모델 정책 apikey project 단위 호출 자격 증명 ai Unified Chat API, provider 어댑터·라우터, 사용량 원장 ├ provider openai / claude / gemini — 형식 변환만 담당 ├ tool provider 중립 tool 정의 └ service 호출 오케스트레이션 context 사내 자료 검색 API, 검색 감사 로그 mcp 개발 AI 도구용 JSON-RPC 엔드포인트 pii 민감정보 검출·마스킹, 정책, 검출 로그 budget 한도 예약·정산·보상 observability 지표 정의, 관리 포트 경계 검사 common 에러 코드, traceId 필터, HTTP 타임아웃

pii, budget, observability는 나중에 붙었지만 기존 모듈을 열어 고칠 필요가 거의 없었습니다. 통제가 들어갈 자리가 호출 오케스트레이션 한 곳으로 모여 있었기 때문입니다.

요청 하나가 지나는 길

POST /api/v1/chat/completions 하나에 통제 계층이 순서대로 걸립니다. 순서 자체가 설계 판단입니다.

API key 인증
JWT가 아니라 project 단위 API key. 호출 주체가 사람이 아니라 서비스이기 때문입니다.
허용 모델 검사
가장 싼 검사를 앞에 둡니다. 정책 위반이면 여기서 끝냅니다.
민감정보 검사 · 마스킹
외부로 나가기 전 마지막 지점. 차단되면 예산을 쓰지 않습니다.
예산 선점
차단될 요청이 먼저 한도를 갉아먹으면 정상 요청이 밀려납니다.
provider 라우팅 · 호출
Bulkhead → CircuitBreaker → Retry가 겹겹이 감쌉니다. 실패하면 허용된 다른 provider로.
tool 실행 (필요 시)
모델이 사내 문서를 요청하면 KAIROS가 대신 실행하고, 그 결과도 다시 민감정보 검사를 거칩니다.
토큰 정산 · 원장 기록
응답이 와야 토큰 수가 확정됩니다. 원장에 못 남기면 응답을 내보내지 않습니다.
provider 어댑터가 하는 일과 하지 않는 일

어댑터는 형식 변환만 합니다. OpenAI의 tool_call, Claude의 tool_use, Gemini의 functionCall을 공통 형식으로 옮기는 것까지입니다. 인증·정책·한도·기록은 전부 그 바깥에 있어서, 새 provider를 붙일 때 통제를 다시 구현하지 않습니다.

04

인증·권한과 정책 계층

사람이 부르는 경로와 서비스가 부르는 경로를 다른 자격 증명으로 나눴습니다.

경로자격 증명권한 판정
플랫폼 관리 APIJWT (access / refresh)전역 역할 + tenant 내 역할
Unified Chat APIproject API keyproject 정책 (허용 모델·도구)
Context API · MCPJWT사용자가 속한 tenant의 project만

경계는 두 겹

tenant는 조직 경계, project는 기능 단위입니다. 금융지주라면 tenant가 계열사, project가 그 안의 개별 AI 기능이 됩니다. 비용도 정책도 감사 로그도 이 두 축으로 갈립니다.

역할은 전역(USER/ADMIN)과 tenant 내 (OWNER/ADMIN/MEMBER)로 분리했습니다. 전역 관리자와 특정 계열사의 관리자는 다른 권한이기 때문입니다.

API key는 원문을 저장하지 않는다

// 발급 시 원문은 한 번만 응답에 실리고, DB에는 해시만 남는다.
val credential = apiKeyRepository
    .findByKeyHashAndDeletedAtIsNullAndRevokedAtIsNull(tokenHasher.hash(apiKey))
    ?: throw KairosException(AI_INVALID_API_KEY)

if (credential.expiresAt?.isBefore(Instant.now()) == true)  throw ... // 만료
if (credential.project.status != ProjectStatus.ACTIVE)      throw ... // project 비활성

키가 유출되어도 DB 덤프만으로는 재사용할 수 없고, 만료·폐기·project 상태를 매 호출마다 확인합니다. 폐기는 삭제가 아니라 revoked_at 기록이라, 사후에 "언제부터 막혔나"를 답할 수 있습니다.

정책은 project에 붙는다

  • 허용 모델 — 같은 게이트웨이를 써도 project마다 쓸 수 있는 모델이 다릅니다
  • 허용 자료원 — AI가 접근할 수 있는 사내 문서 범위
  • 민감정보 정책 — 타입별 차단/마스킹/통과
  • 예산 — 일·월 단위 호출·토큰 한도

민감정보 정책 테이블은 비어 있는 것이 정상입니다. 기본값을 코드가 들고 있어 한 건도 넣지 않아도 통제가 동작하고, 기본값과 다르게 운영할 때만 행이 생깁니다. 새 project를 만들 때 seed가 필요 없습니다.

05

통제 계층 네 가지

망분리가 바깥 경계라면, 이 네 가지는 그 안에서 호출 하나하나에 적용되는 안쪽 통제입니다.

① 민감정보 통제 — 나가기 전에 막는다

주민등록번호, 외국인등록번호, 카드번호, 계좌번호, 휴대전화, 이메일, 여권번호 7종을 검출합니다. 정규식만으로 끝내지 않고 카드번호는 Luhn 체크섬, 주민번호는 생년월일 유효성을 함께 확인합니다. 오탐으로 서비스를 못 쓰게 만들면 결국 우회되고, 우회된 통제는 없는 것과 같기 때문입니다.

검사 지점 세 곳

한 곳만 막으면 구멍이 남습니다. 사용자 프롬프트, 사내 문서 검색 결과가 provider로 되돌아가는 경로, 개발 AI 도구가 보낸 검색 질의 — 세 곳 모두를 지납니다. 두 번째가 가장 놓치기 쉬운 경로입니다.

감사 로그가 유출 경로가 되지 않도록

검출 로그에는 원문도, 마스킹 전 값도, 값의 일부도 저장하지 않습니다. 남기는 것은 어떤 타입이 몇 건 검출되어 어떻게 처리됐는가뿐이고, 요청 단위 추적은 traceId로 다른 로그와 이어 붙입니다. 차단 응답 메시지에도 값이 담기지 않도록 테스트로 못 박았습니다.

성능 측정에서 찾은 서비스 거부 취약점

이메일 정규식에만 앞쪽 경계 검사가 빠져 있어, 정규식 엔진이 모든 위치에서 재시도했습니다. 비용이 입력 길이의 제곱으로 늘어 프롬프트 하나로 CPU를 몇 분간 붙잡을 수 있었습니다. 모든 AI 요청이 거치는 계층이라 보안 기능이 그 자체로 공격 통로가 된 사례입니다.

② 한도·예산 통제 — 동시 요청에서도 정확하게

AI 호출은 실행 전에 소비량을 알 수 없습니다. 토큰 수는 응답이 와야 확정됩니다. 그래서 카드 결제의 승인 → 매입 → 취소와 같은 예약·정산·보상 구조로 설계했습니다.

한도 판정은 애플리케이션이 하지 않습니다. 조건을 UPDATE 문의 WHERE 절에 넣어 DB의 행 단위 원자성에 맡기고, 애플리케이션은 영향받은 행 수만 봅니다. 

UPDATE project_budget
   SET consumed_requests = consumed_requests + 1
 WHERE project_id = :projectId
   AND consumed_requests + 1 <= request_limit    -- 0행이면 한도 초과

비관적 락은 AI 응답을 기다리는 수 초 동안 행을 잡아 처리량을 무너뜨리고, 낙관적 락은 경합이 심한 단일 행에서 재시도가 폭증합니다. 트랜잭션 경계도 UPDATE 하나 단위로 잡아, 호출을 감싸는 트랜잭션 안에서 잠금이 유지되지 않게 했습니다.

장치막는 문제

CircuitBreaker죽은 provider를 계속 두드리며 지연을 쌓는 것

4xx로 서킷을 열면 안 됩니다. provider는 멀쩡한데 우리 요청이 잘못된 상황에서 서킷을 열면 스스로 길을 막는 셈입니다. Resilience4j 판정을 예외 타입이 아니라 에러코드로 하도록 predicate를 따로 두었습니다.

대체 후보는 project_allowed_model에서만 고릅니다. 허용된 대체 모델이 없으면 대체하지 않고 그대로 실패합니다 — 가용성보다 통제를 우선한 선택입니다. 장애 대응이 권한 통제를 우회하면 "장애가 났으니 정책 밖 모델로 우회했다"는 사고가 됩니다.

④ 실패를 한 덩어리로 세지 않는다

통제가 작동한 것과 장애가 난 것을 같은 그래프로 보면 운영에서 구분할 수 없습니다. 에러코드로 나눠 세고, 그 코드가 그대로 대시보드의 계열이 됩니다.

07

관측과 추적

감사에서 답해야 하는 질문은 "그 호출을 재구성할 수 있는가"입니다. 로그가 흩어져 있으면 답할 수 없습니다.

traceId로 세 개의 로그를 잇는다

// 요청마다 부여하고 응답 헤더로 돌려준다. 외부에서 넘어온 값이 있으면 이어받는다.
val traceId = request.getHeader("X-Trace-Id")?.takeIf { it.isNotBlank() }
    ?: UUID.randomUUID().toString().replace("-", "")

MDC.put("traceId", traceId)
response.setHeader("X-Trace-Id", traceId)
// 서블릿 스레드가 재사용되기 전에 반드시 비운다
finally { MDC.clear() }

같은 traceId가 애플리케이션 로그, ai_usage_log(호출 원장), context_search_log(자료 검색), pii_detection_log(민감정보 검출)에 함께 남습니다. 원문 없이도 하나의 요청을 재구성할 수 있는 이유입니다.

로그남기는 것남기지 않는 것
ai_usage_logprovider·모델·토큰·지연·상태·에러코드·대체 이력프롬프트 내용
context_search_log검사를 마친 질의, 자료원, 결과 수차단된 원문 질의
pii_detection_log타입·건수·처리 방식값의 어떤 조각도

원장은 append-only

사용량 로그에는 수정·삭제 흐름을 두지 않았습니다. provider와 모델 이름도 enum이 아니라 호출 시점의 문자열 스냅샷으로 저장합니다. 나중에 enum이 바뀌어도 과거 기록의 해석이 달라지지 않습니다.

집계는 DB, 건강 상태는 지표

"어느 project가 얼마나 썼는가"는 QueryDSL 집계 API가 답합니다 — tenant/project 단위 요약, project별·provider별·모델별 분해. 지표에는 넣지 않습니다. project는 계속 늘어나는 값이라 태그로 쓰면 시계열이 무제한이 되기 때문입니다.

지표는 시스템이 지금 건강한가만 봅니다. 태그는 전부 enum이라 운영 중에 종류가 늘어날 수 없고, 실수로 늘어나는 값을 넣으면 테스트가 막습니다.

08

막혔던 지점과 해결 과정

전부 테스트는 통과하는데 숨어 있던 문제들입니다. 기능을 더 붙이는 대신 이미 만든 것을 다시 재보는 데 시간을 썼습니다.

① 보안 기능이 서비스 거부 통로가 되어 있었다
증상
민감정보 검출 성능을 재보다가, 숫자만 긴 입력에서 입력이 2배면 시간이 4배가 되는 것을 발견했습니다.
원인
규칙 일곱 개 중 이메일 정규식에만 앞쪽 경계 검사가 빠져 있었습니다. 정규식 엔진이 모든 시작 위치에서 재시도하면서 비용이 입력 길이의 제곱으로 늘었습니다.
해결
나머지 규칙이 모두 갖고 있던 경계 검사를 붙이고 각 구간에 상한을 두었습니다. 120초 초과 → 104ms. 20,000자 메시지 50개 기준입니다.
배운 것
모든 요청이 지나는 계층은 정확성만큼 비용의 상한이 중요합니다. 회귀 테스트로 2초 제한을 걸어 두었습니다.
② 한도 통제가 정말 동작하는지 스스로 의심했다
상황
조건부 원자적 UPDATE로 한도를 지키게 만들고 테스트도 통과했지만, 이 테스트가 정말 의미가 있는지 확신이 없었습니다. 잘못 만든 구현도 통과할 수 있기 때문입니다.
확인 방법
일부러 조회 후 판정 방식을 임시로 만들어 같은 조건(가상 스레드 300 동시 요청, 한도 100)으로 돌렸습니다.
결과
조회 후 판정은 300건이 모두 통과했고 원장은 갱신 손실로 5에 머물렀습니다. 조건부 UPDATE는 정확히 100건만 통과시켰습니다.
배운 것
동시성 테스트는 틀린 구현이 실패하는지까지 확인해야 의미가 생깁니다.
③ 락을 피하려고 만든 구조가 락이 될 뻔했다
증상
예산 리포지토리 테스트가 No EntityManager with actual transaction available로 전부 실패했습니다.
고민
@Transactional을 붙이면 되는 문제였지만 어디에 붙이느냐가 설계의 성패였습니다. 예약·AI 호출·정산을 한 트랜잭션으로 묶으면, 응답을 기다리는 수 초 동안 예산 행의 잠금이 유지됩니다.
해결
UPDATE 하나가 자기만의 짧은 트랜잭션에서 끝나게 리포지토리 메서드 단위로 경계를 잡았습니다. 비관적 락을 피하려고 만든 구조가 그대로 비관적 락이 되는 것을 막았습니다.
④ 장애 대응이 중간에 끊겼다
증상
대체 provider 후보가 여럿일 때, 첫 후보가 요청을 거절하면 남은 정상 provider를 시도하지 않고 요청이 끝났습니다.
영향
사용자는 원래 장애가 아니라 마지막 후보가 낸 엉뚱한 오류를 받았습니다. 아직 멀쩡한 provider가 있는데도요.
해결
후보 실패는 원래 예외에 suppressed로 붙여 두고 다음 후보로 넘어가게 했습니다. 모두 실패하면 원래 장애를 그대로 돌려줍니다.
배운 것
예외 흐름은 정상 흐름보다 테스트가 얕아지기 쉽습니다. 시나리오를 하나 더 늘려서야 드러났습니다.
⑤ 설정 한 줄이 빠지면 지표가 공개되고 있었다
배경
지표 엔드포인트에 인증을 걸지 않는 대신 포트 자체를 경계로 삼았습니다. Prometheus가 주기적으로 긁어갈 때마다 토큰을 요구할 수 없기 때문입니다.
문제
그 전제가 깨지면 아무것도 막지 않습니다. 관리 포트 설정을 비운 상태로 실행하니 서비스 포트에서 전체 지표가 인증 없이 200으로 나왔습니다.
해결
설정으로 막는 대신 그런 설정으로는 기동하지 않게 했습니다. 엔드포인트를 끄는 값은 노출 위험이 없으므로 허용합니다.
⑥ 인프라를 올리기 전에 여섯 군데가 깨져 있었다
배경
terraform validate는 문법만 봅니다. 실제로 올려보면 돈은 나가는데 시스템이 뜨지 않는 종류의 문제는 잡히지 않습니다.
찾은 것
대표적으로, NAT 인스턴스에 Elastic IP가 붙기 전에 기동 스크립트가 실행되어 프록시가 설치되지 않은 채 뜨는 문제였습니다. apply는 성공하고 통제 지점만 비어 있는 상태가 됩니다. 그 밖에 프록시 설정보다 먼저 패키지를 받으려 한 것, Squid 규칙 순서가 뒤집힌 것 등 여섯 건입니다.
확인 방법
기동 스크립트를 실제로 렌더링해 iptables·Squid 규칙을 눈으로 확인하고 셸 문법까지 검사했습니다.
배운 것
인프라 코드도 "검증이 통과했다"와 "동작한다"는 다릅니다. 올리기 전에 재볼 수 있는 것은 재보는 편이 시간과 비용 모두 아꼈습니다.
09

설계 판단

기능 목록보다 이쪽이 이 프로젝트의 내용에 가깝습니다. 각 판단에는 포기한 것이 있습니다.

감사 기록에 실패하면 응답을 버린다

provider 호출은 성공했는데 원장에 남기지 못하면 응답을 내보내지 않습니다. 이미 발생한 비용을 버리게 되지만, 누가 무엇을 외부로 보냈는지 기록 없이 결과만 나가면 그 호출은 사후에 재구성할 수 없습니다. 추적할 수 없는 호출이 비용보다 큰 문제라는 판단입니다. 반대로 실패 경로에서는 기록 실패를 삼킵니다 — 요청이 어차피 실패로 끝나 막아야 할 "기록 없는 성공"이 없고, 여기서 예외를 올리면 원래 실패 원인이 DB 오류로 바뀌어 진짜 문제를 가립니다.

민감정보 검사가 예산 선점보다 먼저

차단될 요청이 먼저 한도를 갉아먹으면 정작 정상 요청이 밀려납니다. 주민번호를 반복 전송하는 것만으로 그 project의 하루 한도를 소진시킬 수 있게 됩니다.

검색 질의 검사는 예외 처리 바깥에서

차단된 질의가 catch 블록으로 흘러가면 원문이 검색 감사 로그에 그대로 적재됩니다. 막으려던 유출이 감사 로그로 새는 셈이라 검사 순서를 뒤집었습니다. 차단 사실은 별도 로그에 남으므로 감사에 공백은 생기지 않습니다.

기간 초기화를 스케줄러로 하지 않는다

스케줄러를 두면 인스턴스가 여러 대일 때 중복 실행 문제가 새로 생깁니다. 요청 시점의 조건부 UPDATE로 처리하면 자정 직후 동시에 들어온 요청 중 정확히 하나만 초기화에 성공합니다.

토큰은 사후 정산이라 한 요청만큼 초과될 수 있다

호출 전에 토큰 수를 알 수 없으므로 구조적으로 불가피한 오차입니다. 정산에는 한도 조건을 걸지 않습니다 — 이미 발생한 사용량을 남기지 않으면 원장이 어긋나고, 한도를 넘긴 상태는 다음 요청의 예약이 막습니다.

허용 목록에 provider 도메인만 있는 것은 아니다

OS 패키지 저장소와 컨테이너 레지스트리도 들어 있습니다. 인터넷이 없는 구간에서 부팅하려면 어딘가는 열려야 하기 때문이고, 실무에서도 사내 미러를 두거나 같은 형태의 목록을 유지합니다. 통제를 느슨하게 한 것이 아니라 목록에 명시했다는 점이 다릅니다.

검증

  • 통합 테스트는 Testcontainers로 실제 PostgreSQL에 마이그레이션을 적용하고, ddl-auto=validate로 엔티티와 스키마가 어긋나면 컨텍스트가 뜨지 않게 했습니다.
  • 동시성은 가상 스레드로 실제 경합을 만들어 검증합니다. 요청을 한 줄로 세워 확인하면 주장 자체를 검증하지 못합니다.
  • 장애는 응답을 조작하는 서버를 provider 자리에 놓고 호출 횟수를 세어 확인합니다. "설정했다"가 아니라 "몇 번 호출됐나"로 증명합니다.
  • 부하는 k6로 mock provider 3초 지연 조건에서 200 VUs까지 실패율 0%, p95 3.03초를 확인했습니다.
비용

망분리 환경은 apply → 검증 → destroy 주기로 운영합니다. 기본 구성 기준 시간당 약 ₩75이며, 남는 것은 캡처와 Terraform 코드입니다. 재현할 수 없으면 산출물이라 할 수 없다는 기준으로 인프라를 코드로 관리했습니다.

11

한계

과장하지 않기 위해 적습니다. 아래는 알고 남겨둔 것들입니다.

  • Squid는 Network Firewall의 대체재입니다. 판정 방식(도메인 허용 목록)은 같지만, 실무에서는 관리형 방화벽이나 보안 웹 게이트웨이가 맡는 자리입니다. 비용 제약 때문에 대체했습니다.
  • 계좌번호는 체크섬 검증이 불가능합니다. 은행마다 자릿수 규칙이 달라, 형식이 겹치는 사업자등록번호와 유선전화를 제외하는 방식으로 오탐을 줄였습니다. 그래서 기본 정책이 차단이 아니라 마스킹입니다.
  • 재시도가 서킷 집계를 부풀립니다. Retry가 CircuitBreaker보다 바깥이라 한 요청의 재시도가 슬라이딩 윈도우에 여러 건으로 기록됩니다. 동작은 정상이고 오히려 보수적이지만, 설정값이 보이는 그대로의 의미는 아닙니다.
  • 단일 AZ 구성입니다. 망분리 서사를 보여주는 것이 목적이라 가용성 이중화는 범위 밖으로 두었습니다.
  • 신규 AWS 계정은 프리티어 대상 인스턴스 타입만 만들 수 있습니다. 그래서 NAT에 t4g.nano 대신 t4g.micro를 썼습니다. 사양이 남지만 선택지가 없었습니다.
  • RAG와 실제 사내 문서 연동은 범위 밖입니다. Tool Calling과 MCP로 연결 규격까지 만들었고, 실제 검색 대상은 목업입니다.
이 프로젝트에서 얻은 것

기능을 붙이는 것보다 "설정으로 막았다"와 "구조적으로 못 한다"의 차이를 일관되게 적용하는 쪽에 시간을 더 썼습니다. 라우팅에 경로를 두지 않고, 관리 포트가 분리되지 않으면 기동하지 않게 하고, 지표 태그에 늘어나는 값이 들어가면 테스트가 막게 한 것이 모두 같은 판단입니다.
